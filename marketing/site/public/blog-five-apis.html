Five APIs on Cloudflare Workers, and the four bugs that nearly shipped

Five products, 37 endpoints, 470 tests, one deploy command each. Here is the architecture, the pricing maths, and the four bugs that would have made the whole thing useless.

Cloudflare WorkersHonoOpenAPI 3.0RapidAPI

The shape of the thing

One pnpm workspace, five Workers, one shared package. Each Worker is its own product with its own name, its own key, its own quota and its own failure domain. A bug in the PDF parser cannot take down email verification, and I can ship one without redeploying the other four.

The shared package does the boring, dangerous work once: error envelope, CORS, request ids, timing headers, OpenAPI generation, SSRF-safe fetching, and the RapidAPI proxy-secret check. Every route in every app is registered through app.openapi(createRoute(...), handler) so the spec is generated from the same source of truth as the handler. There is no hand-written YAML to drift out of date.

That gave me 37 endpoints and 470 unit tests. Every app passes tsc --noEmit and every route was answered with a real curl before it was listed anywhere.

Why these five

APIs on a marketplace sell on search intent, not on cleverness. Someone types "email verification api" because their signup flow is leaking bounces. They are not looking for a platform. So the product has to name the job, not the technology.

I avoided the categories that look lucrative and are legally toxic: scraped social profiles, real estate listings, job feeds. Those are someone else's data with someone else's terms attached. Everything here computes something from input you send, or fetches a page you asked about. That constraint is not just ethics, it is what makes the thing durable.

The four bugs

1. The SSRF guard rejected every hostname. My validateHostname() ran the hostname through the private-IP blocker. That blocker reports "blocked" for any string that is not a parseable IP, so example.com looked like a private range. Every fetch-based endpoint returned a 400 before making a single request. A teammate building the SEO app found it and shipped a workaround, which is exactly the right instinct: unblock yourself, report the bug, delete the workaround once it is fixed.

2. A UTF-8 BOM broke the OpenAPI import. PowerShell's Set-Content -Encoding UTF8 writes a byte order mark. The marketplace's importer saw three junk bytes before { and refused the file with "failed to parse JSON content". The fix is boring: download the raw bytes, do not let a shell re-encode them. But the error message pointed at JSON syntax, not at encoding, which is why it cost half an hour.

3. The model I pinned was deprecated. @cf/meta/llama-3.1-8b-instruct resolved to a retired backing model and every summarise call failed with a 5028. The replacement I tried first ignored the chat messages array and only accepted a plain prompt, which produced fluent but deranged output: a 118 word "summary" that repeated "The summary should be made in at most 40 words" until it ran out of tokens. The working answer was a chat-native model plus a parser that accepts both response shapes and a fallback to prompt when the chat shape comes back empty. Model ids are a supply chain dependency, treat them like one.

4. The proxy secret had a trailing newline. Setting it with wrangler secret put from a shell pipe stored uuid\n. The guard compared the header against a value with a newline, failed, and returned 401 for every marketplace request. Trimming both sides before comparing fixed it. If I had tested only "direct call is now rejected" I would have shipped an API that rejected everyone.

Pricing, with the real numbers

The marketplace takes a flat 25% and pays out through PayPal after roughly two months. So a $25 subscription is about $18.75 to me, and it arrives in the new year.

There is no free tier. The entry plan is pay as you go at $0.05 a call with no monthly minimum, then monthly plans at $25, $75 and $150 once volume makes them cheaper. A free tier that covers the real use case kills the paid one, and a free tier too small to evaluate anything is just a teaser. Metering solves both: you pay for exactly what you test.

Marginal cost per call is close to zero for three of the five: DNS and HTTP lookups are cached at the edge, PDF parsing and PII detection are CPU on a single Worker. The exceptions are real and priced for: the neural endpoints bill per token to Workers AI, so they are capped per request, and the fetch-based ones make live network calls that no amount of pricing can make free.

What I would tell the next person

Build one endpoint you can explain in a sentence, then make the response explain itself. Every verdict in these APIs ships with the reasons behind it, because the moment a buyer cannot explain a score to their own manager, they stop trusting the API and cancel.

Write the limitation into the product. EmailCheck says outright that it cannot prove a mailbox exists without an SMTP handshake, so it verifies domain deliverability and risk signals instead. Buyers forgive a documented limit. They do not forgive discovering one in production.

And test the path a customer actually takes. My proxy-secret bug survived local testing, unit tests and a live smoke suite, and was only caught by running a request through the marketplace itself.
