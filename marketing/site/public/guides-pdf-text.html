PDF text extraction that runs where your code already runs

Parsers assume a filesystem, a canvas and a few hundred milliseconds of CPU you may not have. A POST is easier than a runtime.

Why this is annoying in a worker

Most PDF libraries pull in a native canvas for layout, assume Node built-ins, or want 300ms of CPU per page. In an edge runtime that is either unavailable or priced differently than you expect. The alternative is to move parsing out of your process entirely.

The request

Send a URL or a base64 payload. URL is better for anything large: no encoding cost, and the fetch happens on our side.

curl -s -X POST 'https://docparse.p.rapidapi.com/v1/pdf/text' \
  -H 'Content-Type: application/json' \
  -H 'X-RapidAPI-Key: YOUR_KEY' \
  -H 'X-RapidAPI-Host: docparse.p.rapidapi.com' \
  -d '{"url":"https://arxiv.org/pdf/1810.04805"}'
const res = await fetch('https://docparse.p.rapidapi.com/v1/pdf/text', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-RapidAPI-Key': process.env.RAPIDAPI_KEY,

POST /v1/html/markdownclean markdownfeeding a model or a CMS

Limits, stated plainly

  • No OCR. A scanned PDF has no text layer, so the text comes back empty. That is a different service.
  • Encrypted or password-protected files are rejected with a clear error rather than a partial parse.
  • A 100-page, 45,000-word PDF takes about three seconds. A 16-page paper is under one.
  • Nothing is stored. The file is held in memory for the request and dropped.
